BA ↔ Engineering · Working agreement proposal

A confirmed-state boundary between BA analysis and engineering delivery

Right now, requirements, decisions, and RAID items live in BA working docs that shift daily - and devs pick up whatever version they can find. This proposes a clear line: nothing crosses into "confirmed" without passing a structured check, and once it does, it's dated, stable, and yours to build on.

From: BA Date: 7 Jul 2026 Status: Proposal for feedback Ask: Reaction to the principle, not sign-off on the folder layout
This is a proposal, not a spec. The folder names, file paths, and exact mechanics shown below (e.g. confirmed/, exchanges/) are illustrative - the point being tested is the principle: a gated, dated, one-way boundary between draft analysis and things safe to build on. If a different structure works better for how you already work, that's an open question, not a constraint.
01 - Problem

What's causing rework today

No confirmed/draft distinction

A requirement in a BA doc might be a first-pass idea or a stakeholder-agreed decision - from the outside, they look identical. Devs sometimes build against the wrong one.

Shared editing surface

BAs and devs sometimes end up working in or around the same working files. Edits collide, provenance gets lost, and it's unclear who last touched what.

No visible "as of" date

A requirement handed over in May can quietly go stale by July with no signal - the dev has no way to tell it's drifted from current thinking.

Vague asks bounce back

Spikes and ADR requests without a clear linked decision or a "done looks like" come back with "what do you actually want" - that round-trip is pure rework.

02 - What's proposed

Two kinds of thing, kept physically apart

Everything BA-side stays working and constantly changing. Nothing crosses the line into the shared space until it's deliberately confirmed.

Working (BA side only)

  • Session notes, meeting debriefs, draft requirements
  • RAID tracker (risks, decisions, dependencies) - changes constantly
  • Changes daily, sometimes hourly
  • Devs never read this directly - and never need to

Confirmed (safe to build on)

  • Requirements that passed interrogation + stakeholder agreement
  • Agreed current-state, ADRs, DoR-passed stories
  • Every artefact carries a "Last confirmed: [date]" header
  • Overwrites on republish - last confirmed always wins, no ambiguity about which version is live

Exchanges (the two-way conversation space)

Spike requests, ADR requests, and their results live here - append-only. A new spike is a new dated file, never an edit to a closed one, so there's a permanent record of what was asked, when, and what came back. This is the "exchange" you mentioned: BAs and devs both write here, but never to the same file at the same time - a request in, a result back, each its own dated artefact.

03 - How it runs

The gate: nothing is "confirmed" without passing through this

Confirmation and publication are two separate events. A requirement earns status: confirmed in the BA's register through a structured interrogation conversation and stakeholder agreement - that always happens first, on its own. Publishing to the shared space never confirms anything as a side effect; it only ever renders what's already confirmed.

04 - The gates in detail

What has to be true before anything publishes

06 - How this relates to OpenSpec / spec-driven development

Same philosophy, different layer of the pipeline

OpenSpec (and Spec Kit, Kiro, etc.) are spec-driven-development tools that sit inside a code repo and gate what an AI coding agent is allowed to build. This proposal is upstream of that - it's the boundary between BA analysis and whatever spec/ticket/code process picks it up next, OpenSpec included.

Where they'd connectA confirmed requirements pack from this process is a natural input to an OpenSpec (or Spec Kit / Kiro) proposal - it's already agreed, dated, and EARS-renderable. This isn't a competing tool; it's the upstream agreement layer that a downstream spec-driven tool could consume.
